01 · Overview

A bounded, read-only observability run

The automation collects operational signals from a configured GKE or Kubernetes cluster and produces one reviewable snapshot.

On demand or scheduled

Scope: read cluster objects and recent logs, collect current resource metrics, query optional telemetry backends, check basic health, and flag node CPU or memory at the configured threshold.

02 · Use case / problem statement

Cluster signals are spread across separate tools

Operators need a repeatable first-pass health check without manually collecting each signal from multiple endpoints.

Operational problem

Manual collection takes time

Cluster state, recent logs, metrics, Prometheus history, and trace search live behind different APIs and queries.

Snapshots are hard to compare

Without a consistent collection window and output shape, an incident handoff can miss context or use stale readings.

Resource pressure needs a clear signal

CPU and memory should be evaluated against node capacity, with one configurable threshold and an explicit breach list.

Automation response

Run one read-only collector to join the available signals, summarize basic health, record partial failures, and notify the configured team when a threshold is reached.

03 · Architecture

Four signal paths feed one collector

Kubernetes and Metrics Server are the core sources. Prometheus and trace search are enabled only when configured.

05 · Scope and raw code

What the automation reads and returns

The code panel below loads the current k8s_observability.py file from this project.

Project source

Included

  • Read-only Kubernetes inventory, events, and bounded recent pod logs.
  • Current node and pod CPU/memory samples from Metrics Server.
  • Node usage percentages against allocatable capacity; default threshold is 80% inclusive.
  • Optional Prometheus range queries and backend-specific trace search.
  • Health summary, threshold breach list, JSON snapshot, optional SMTP notification.

Operational boundary

  • No agents installed and no cluster resources changed.
  • Long-term logs and traces remain in their configured backends.

How the Python collector works

  1. Load configuration. Read the cluster context, collection limits, threshold, and optional backend settings from YAML.
  2. Connect and collect. Use the Kubernetes client to read inventory, events, and recent logs; section failures are recorded.
  3. Read telemetry. Fetch current Metrics Server samples, then query Prometheus and the trace search endpoint when enabled.
  4. Evaluate health. Convert CPU and memory quantities, compare each node with allocatable capacity, and check API, node, and pod status.
  5. Write and notify. Combine results and errors in a UTC-stamped JSON file; send SMTP email for a threshold breach when configured.
Threshold math: CPU % = used cores ÷ allocatable cores. Memory % = used bytes ÷ allocatable bytes. The default breach point is 80% inclusive. Metrics Server is a current sample; Prometheus supplies history.
